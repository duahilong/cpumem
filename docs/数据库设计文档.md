# CPU/内存/硬盘 价格数据库设计文档

> 本文档总结价格数据库的完整设计：数据结构、提取流程、提示词体系、运行方式。
> 数据来源：`价格图片/` 目录下的硬件报价单截图（已手动分类：CPU / mem / TF / 其他）。

---

## 一、项目目标

把报价单图片中的价格信息提取出来，存入结构化数据库，支持以下核心查询：

1. **某型号 CPU 一段时间内的价格波动**（折线图展示）
2. **某型号某一天的价格**
3. **某型号硬盘/内存的价格波动**

核心两轴：**时间** 和 **价格**。

---

## 二、整体流程

```
价格图片/（手动分类：CPU/mem/TF/其他）
   │
   ▼
① 三条独立提取管线（按类目分开，互不影响）
   ├─ extract_cpu.py  CPU 专用管线：只处理 价格图片/CPU/
   │                  左半裁剪预处理 + CPU 白名单 → extracted_cpu/
   ├─ extract_mem.py  MEM 专用管线：只处理 价格图片/mem/
   │                  提示词 = base.txt + mem.txt，不施加 CPU 白名单
   │                  保留图片全部类目 + hardware_type 类别缩写补齐 → extracted_mem/
   └─ extract.py      通用管线（其他类目）：递归全部分类目录
                      提示词 = base.txt + <分类>.txt + CPU白名单 → extracted/
   ▼
② clean_load.py   清洗规范化 → 写入 SQLite（幂等）
   │               - 日期规范化（年份强制 2026）
   │               - 品牌/大类/价格类型归一
   │               - 型号名规范化（product_key）
   │               - 过滤：price<=0、含*/X 的无效价格
   │               - 去重：同日同型号同类型，同价留一条，异价进 conflicts.json
   ▼
③ cpumem.db       SQLite（products / dates / quotes 三表）
   │
   ▼
④ 查询/画图        SQL 时间序列查询 → 折线图
```

## 三、分类体系

三级归属：**大类 → 品牌 → 型号**

```
大类 (category)      品牌 (vendor)            型号示例
─────────────       ─────────────           ─────────────
CPU                 Intel / AMD              i5-12400F / Ryzen 5 5600
内存                金士顿 / 三星 / 金百达...   FURY 16G 6000 / 银爵 8G/3200
固态硬盘            三星 / 西数 / 金士顿...     990 PRO 1TB / SN770 2TB
机械硬盘            西数 / 希捷               WD10EZEX / ST1000VX009
主板 / 显卡 / 电源 / 显示器                  微星 B760M / 影驰 RTX 5070
TF卡 / SD卡 / U盘   金士顿 / 闪迪             TF卡 SDCS3 16G
```

- 大类/品牌 vocabulary 固定并归一（"Kingston"→"金士顿"），定义在 clean_load.py 的映射表

## 四、数据结构（星型模型）

```
dates (日期维)          products (型号维: 分类+品牌)        quotes (价格事实)
┌──────────────┐      ┌──────────────────────────┐      ┌─────────────────────┐
│ 2026-09-16   │◄─────│ i5-12400f | CPU | Intel  │◄─────│ ..., 613, 散片      │
│ 2026-09-15   │      │ kingston-nv3-1tb |内存|金士顿│    │ ..., 720, 原盒      │
└──────────────┘      └──────────────────────────┘      └─────────────────────┘
```

### 4.1 products（型号维表）

```sql
CREATE TABLE products (
    product_key   TEXT PRIMARY KEY,  -- 规范化键，如 'i5-12400f'
    display_name  TEXT NOT NULL,     -- 展示名，如 'Intel i5-12400F'
    category      TEXT NOT NULL,     -- 大类
    vendor        TEXT NOT NULL      -- 品牌
);
```

### 4.2 dates（日期维表）

```sql
CREATE TABLE dates (
    date_key   TEXT PRIMARY KEY,     -- 'YYYY-MM-DD'
    year INTEGER, month INTEGER, day INTEGER, weekday INTEGER
);
```

### 4.3 quotes（价格事实表）

```sql
CREATE TABLE quotes (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    product_key   TEXT NOT NULL REFERENCES products(product_key),
    date_key      TEXT NOT NULL REFERENCES dates(date_key),
    price         REAL NOT NULL,
    price_type    TEXT DEFAULT '默认', -- 散片/原盒/单条/套装/默认
    source_image  TEXT                 -- 来源图片（溯源）
);
CREATE INDEX idx_q_prod_date  ON quotes(product_key, date_key);
CREATE INDEX idx_p_cat_vendor ON products(category, vendor);
```

### 4.4 关键设计决策

#### ① 一个价格 = 一行记录（长表）
双价行（如 `i3 10100F  375/490`）拆成两条：散片 375 + 原盒 490。
- `price_type` 维度：任何型号任何价格类型都是同一条 SQL；新价格类型无需改表
- 取值约定：CPU=散片/原盒；内存=单条/套装；兜底=默认

#### ② 日期从图片标题提取，年份强制 2026
图片中只有月日；LLM 输出年份错误时，clean_load 强制改为 2026。

#### ③ product_key 规范化
统一小写/去空格/统一连接符，解决写法漂移（`i5 12400F` / `I5-12400F` / `i5-12400F`）。

## 五、提取流程（extract.py）

### 5.1 模型配置（llm_config.json，本地填写密钥）

```json
{
  "base_url": "http://10.0.0.21:8311/v1",
  "api_key": "xxx",
  "model": "sensenova-6.8-flash-lite",
  "temperature": 0,
  "extra_body": { "reasoning_effort": "none", "thinking": { "type": "disabled" } }
}
```

**模型选型结论（多模型实测对比）**：

| 模型 | 耗时 | 质量 | 结论 |
|---|---|---|---|
| **sensenova-6.8-flash-lite** | 100~160s | ✅ 准确、无幻觉 | **生产采用** |
| glm-5.3-flash | 560s | 较全但少量错位 | 备选 |
| qwen3.8-27b | 108s | 有跨区幻觉 | 备选 |
| deepseek-v4.1-flash | 16~21s | 随机错位严重 | 不用 |
| kimi-k3 | 143s | 漏提多 | 不用 |

**关键经验**：reasoning 模型（sensenova/glm 系）开思考会耗尽 65536 token 上限导致 JSON 截断（content 为空），必须关闭思考（reasoning_effort=none + thinking=disabled）。准确性靠提示词规则保证，不靠思考。

### 5.2 提示词体系（prompts/ 目录，外置可随时修改）

```
prompts/
├── base.txt      # 公共基础规则（所有分类通用）
├── CPU.txt       # CPU 专用规则
├── mem.txt       # 内存专用规则
├── TF.txt        # TF卡专用规则
└── 其他.txt      # 混合类专用规则
```

组装逻辑：`最终提示词 = base.txt + <图片所在文件夹名>.txt + CPU白名单`
- 图片在 `CPU/` 文件夹 → 加载 `prompts/CPU.txt`
- 新增分类文件夹时，在 prompts/ 下加同名 txt 即可
- 修改提示词直接编辑 txt，下次提取立即生效（实时读取）

#### base.txt 核心规则
1. JSON 输出 5 字段：category/vendor/product_name/price_type/price
2. 日期年份固定 2026
3. 无效价格剔除：星号/X/空 → 跳过；`****/853` 只保留有效价
4. **严禁跨行复制价格**：空价格行直接跳过（防幻觉）
5. 只输出 JSON，5 字段，不要 spec/price_raw/note

#### CPU.txt 核心规则
1. **拆行总则**：先数 N 型号 M 价格再拆
   - 1型号+2价 → 散片/原盒两条
   - N型号+N价 → 按型号拆（如 `U5 230F-245KF-245K 12/85/238`）
   - 2型号+3价 → 按列头位置严格对应
2. **逐行对齐校验**：价格必须能说出对应型号位置；同型号不能多条不同价；价格量级要合理；对不上就跳过不猜
3. **行结构识别**：U5/i5/Ryzen 开头是新型号标志；型号名内 `-` 是规格不是分隔符

### 5.3 CPU 白名单（cpu_watchlist.json）

```json
{
  "enabled": true,
  "Intel": ["i3 10100", ..., "U9 285K"],   // 第10代及以后，61 个型号
  "AMD": "全部"
}
```

- 写入 Prompt 限制提取范围（LLM 端过滤），输出量减少 → 准确率提升
- 匹配规则：双型号行拆开判断、前缀变体（US=U5）、后缀变体（F/K/KF 独立判断）
- `enabled: false` 可随时关闭；编辑型号清单后下次提取生效

### 5.4 运行方式与断点续跑

```bash
python extract.py                # 批量提取（10并发，断点续跑）
python extract.py --file 图片名.png   # 单张测试
python extract.py --status       # 查看提取进度
```

**断点续跑机制**：每张图提取完立即落盘 `extracted/<文件名>.json`；重跑自动跳过已完成的；失败的不写 JSON，重跑自动重试。中途关机/中断后重新运行即可从断点继续。

**并发**：MAX_WORKERS=10（可改）。注意部分网关路由不稳定时会有少量请求失败，重跑即可。

## 五之二、MEM 专用提取管线（extract_mem.py）

> MEM 管线与通用 extract.py 完全独立，只处理 `价格图片/mem/` 目录，避免与其他类目的提示词/白名单/输出互相干扰。

### 5.2m 管线设计

```
价格图片/mem/*.png|jpg|jpeg        （只扫描 mem 子目录）
   │
   ▼
提示词装配（固定，不按父目录动态拼接）
   ├─ prompts/base.txt             # 通用 JSON 契约
   └─ prompts/mem.txt              # 内存专用规则
   （✗ 不加载 CPU/TF/其他 的规则；✗ 不施加 CPU 白名单）
   │
   ▼
调用多模态 LLM（图片整张发送，不做裁剪；10并发，temperature 兼容降级）
   │
   ▼
后处理兜底
   ├─ 保留图片中全部类目（mem 报价单常同时含内存/固态/主板/显卡等，不剔除非内存产品）
   └─ 每条记录补齐 hardware_type 类别缩写字段（LLM 漏填时按 category + 型号名推断）
   │
   ▼
extracted_mem/<图片名>.json       （独立输出目录，含 source_image 溯源）
```

### 5.3m hardware_type 类别缩写字段

mem.txt 要求每条记录额外输出 `hardware_type`，表示该硬件的类别缩写：

| category | hardware_type |
|---|---|
| 内存 | DDR3 / DDR4 / DDR5（按 DDR 代际细分） |
| 固态硬盘 | SSD |
| 机械硬盘 | HDD |
| 显卡 | GPU |
| 主板 | MB |
| 电源 | PSU |
| 显示器 | MON |
| CPU | CPU |
| 外设 | PERIPH |
| TF卡/SD卡/U盘 | CARD |
| 无法判断 | OTHER |

**DDR 代际识别**（extract_mem.py 的 `infer_ddr_type()` 兜底，LLM 漏填时启用）：
1. 优先匹配型号名中的显式标记（`DDR3/DDR4/DDR5`，容忍空格/大小写）
2. 匹配不到时按频率启发式：4000~12000 → DDR5，800~2133 → DDR4
3. 仍无法判断 → OTHER

实测（开发图 0cd7c…，2026-05-29 期，235 条）：DDR3×8、DDR4×44、DDR5×54、SSD×85、MB×20、GPU×13、MON×11，覆盖 100%，与 category 完全对应。

### 5.4m 运行方式

```bash
python extract_mem.py                # 批量提取 mem 目录（10并发，断点续跑）
python extract_mem.py --file 图片名.png   # 单张测试
python extract_mem.py --status       # 查看提取进度
```

输出：`extracted_mem/`（与 `extracted/`、`extracted_cpu/` 互不影响）、`extract_mem_progress.log`（独立进度日志）。

**注意**：`clean_load.py` 目前读 `extracted/`；extracted_mem 的结果入库需扩展 clean_load.py 或另建入库入口。

## 六、清洗入库（clean_load.py）

```bash
python clean_load.py            # 处理 extracted/ 下全部 JSON
python clean_load.py --force-conflicts   # 冲突记录强制入库（人工确认后）
```

清洗规则：
1. **日期规范化**：`09月16日`/`9.16` → `YYYY-MM-DD`；年份异常强制 2026；从文件名兜底
2. **品牌归一**：Kingston→金士顿 等映射表
3. **大类归一**：SD卡→SD卡（保留细分）、移动固态→固态硬盘、硬盘盒→外设 等
4. **型号规范化**：product_key 生成；新型号自动插入 products
5. **价格过滤**：price≤0（缺货/无价）、含 `*`/`X`、超出 1~200000
6. **幂等**：按 source_image 先删后插，重跑不重复
7. **去重**：同日同型号同类型多条 → 同价留一条；**异价冲突** → 移出库写入 conflicts.json 等人工核对

**增量更新工作流**（未来新增图片）：
```
新截图 → 拖进 价格图片/ 对应分类文件夹
  → python extract.py --real     （只处理新图，老的自动跳过）
  → python clean_load.py         （新数据入库，幂等）
```

## 七、查询示例

```sql
-- ① 某CPU一段时间价格波动
SELECT d.date_key, q.price, q.price_type
FROM quotes q
JOIN products p ON q.product_key = p.product_key
JOIN dates d ON q.date_key = d.date_key
WHERE p.display_name LIKE '%i5-12400F%'
  AND p.category='CPU' AND p.vendor='Intel'
  AND q.price_type='散片'
  AND d.date_key BETWEEN '2026-08-05' AND '2026-09-16'
ORDER BY d.date_key;

-- ② 某天某CPU的价格（去掉 BETWEEN，加 date_key='2026-09-16'）

-- ③ 浏览：某品牌/大类的型号清单
SELECT vendor, display_name FROM products WHERE category='CPU' ORDER BY vendor;
```

折线图 = 时间序列 + matplotlib（单线走势 / 双线对比，如散片 vs 原盒）。

## 九、已知问题与后续优化方向

1. **LLM 提取随机性**：同一张图多次提取结果有差异（temperature=0 也无法完全消除），复杂多型号区域（U 系交织行）偶发价格串行
   - 优化方向：同图多次提取 + 多数一致才入库（majority voting）；或双模型交叉验证
2. **异价冲突**：不同报价单同型号价格体系不同、型号名归并误差都会产生冲突，当前剔除待人工核对
3. **价格缺失**：价格栏空白的型号（缺货/未报价）不产生记录，查询时自然缺失
4. **外部服务路由**：本地网关（Bifrost）偶发路由到不支持多模态的后端，重跑即可

## 十一、提示词迭代优化记录（开发集：0a04 图 + jg.xlsx 人工基准）

> 历史记录说明：本章记录的 `jg.xlsx` / `jg.txt` / `CPU.txt` 已删除（数据已并入 `pricebenchmark/0a04-pricebenchmark.xlsx` 和 `prompts/OCR主_指令.txt`），以下内容保留作为迭代历史参考。

> 迭代方法：固定测试图（CPU/0a04d486...png，2026-03-11 期）+ 人工校对基准（jg.xlsx，54 个有价型号）
> → 提取 → verify.py 比对 → 针对性改 Prompt → 再提取，直至准确率达标。
> 泛化验证：换其他期数的图测试，确认规则没有过拟合。

### 11.1 验证工具（verify.py）

- 读 jg.xlsx（人工基准）与提取 JSON，按型号严格归一后逐项比对
- 型号归一规则：去空格/连字符、统一前缀（'15 12490F'→i512490f、'1I9'→i9）、
  去核数/线程/频率后缀（i312100f4核8线程→i312100f）、集显/带显/傲雪等营销后缀归一、
  双型号行归到第一个型号、'Inte 300'（笔误）与 'Intel 300' 归一
- 错误分类：类型错（数值对但 price_type 错）/ 数值错 / 漏提 / 多提 / 清单外（人工清单未覆盖，不计错）
- 输出准确率报告：`python verify.py <提取JSON>`

### 11.2 数据结构变更

- **JSON 输出简化为 5 字段**：去掉 spec / price_raw / note（规格拼入 product_name；溯源靠 source_image）
- **quotes 表去掉 price_raw 列**：字段为 id / product_key / date_key / price / price_type / source_image
- **clean_load.py 支持自动建表**（cpumem.db 不存在时自动创建，不再依赖 build_db）

### 11.3 图片预处理：左半裁剪（关键改进）

**动机**：报价单右半部分（台式硬盘、金士顿/麦光/紫光内存列）是幻觉源头——多模型测试中
出现"把硬盘价格串给 CPU"、"把内存价格串给 U 系"等跨区串行错误。

**方案**（对 4 类长宽比例通用，无需分别校准）：

```python
top  = img.crop((0, 0, w, int(h*0.062)))             # 顶部标题条全宽（日期 100% 保留）
left = img.crop((0, int(h*0.062), int(w*0.42), h))   # 左半（CPU 全部信息）
canvas 拼接（右侧以白色覆盖，零缩放零清晰度损失）
```

### 11.6 迭代中的关键教训

1. **人工记忆不可靠**：多次"原图实际"凭记忆给出后被推翻（不同期表格结构不同），
   书面基准（jg.xlsx）是唯一可信的比对依据
2. **过拟合风险真实存在**：针对单张图优化的规则（"U 系标原盒"）在其他图上反向生效，
   必须用第二张图做泛化验证
3. **LLM 表格对齐能力是瓶颈**："相邻行串行"（无后缀型号拿到 F 版价格）、
   "列复制"（高亮行价格复制整列）是视觉表格理解的固有局限，
   提示词只能缓解（"不确定就跳过"），不能根治
4. **错误分类很重要**：把错误分为类型错/数值错/漏提/多提，每类的修复手段不同：
   - 类型错 → 列头判断规则
   - 漏提 → "缺一不可"规则 + 自检
   - 多提（无价行复制）→ "严禁跨行复制"规则
   - 数值错（OCR 误差）→ 多次提取投票
